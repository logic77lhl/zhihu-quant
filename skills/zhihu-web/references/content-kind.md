# 回答内容性质：严选/盐选、虚构小说、灌水（2026-10 实测）

> 故事征集题（「有哪些平淡却心酸的暗恋故事？」这类）必读。
> 实测发现**头部排序被虚构内容主导**，而这两种东西在文本上很像、来源却完全不同，
> 处理错了整份报告的结论就是错的。

---

## 0. 先纠正一个想当然的等式

**「知乎严选/盐选」= 商业状态，「小说」= 文体，两者互不包含，不能合并成一个标签。**

实测 question/303487786（3898 条）：

| | 数量 | 其中是虚构 |
|---|---|---|
| 严选/付费 `answer_type=paid` | 22 | **22/22 = 100%** |
| 虚构内容（小说 + 改编，全部） | 625（**16.0%**） | 22 条是严选（**3.5%**） |

即：**严选内容 100% 是虚构，但虚构内容里只有约 3.5% 是严选** —— 多数小说作者是免费发的。
所以两个标签必须分别标、分别筛。

## 1. API 层能拿到的（权威，不用猜）

实测 `/api/v4/questions/<qid>/answers` 的字段（2026-10）：

| 字段 | 位置 | 含义 |
|---|---|---|
| `answer_type` | 顶层 | **三值**：`"normal"` / **`"paid"`** / **`"paid_column_content"`** ← 后两者都是严选/盐选付费内容。**判定一律用 `!== "normal"`；写成 `=== "paid"` 会静默漏掉 `paid_column_content`**（实测 q665321619：normal 1960 / paid 101 / paid_column_content 3） |
| `author.is_advertiser` | `author` 下 | `true` = 广告主账号 |
| `author.user_type` | `author` 下 | `"people"` / **`"organization"`** ← 机构号 |
| `author.badge_v2.detail_badges[].description` | `author` 下 | 「已认证机构号」「知势榜…上榜答主」等 |

**`answer_type` 默认不在返回里 —— 第一次抓取几乎必然漏掉它。**
`fetch-answers-api.mjs` 的 `include=` 已包含这些字段，新抓取不会再漏。

### 补抓（`enrich-flags.mjs`）

只用于补救**在补字段之前抓的旧产物**（`answer_type` 为 `undefined`）。
不用重抓正文，只补这几个标志，快得多：

```powershell
$S = "$env:USERPROFILE\.config\opencode\skills\zhihu-web\scripts"
node "$S\enrich-flags.mjs" q<ID>-answers-full.json <问题ID>
```

实测 396 页 / 3898 条 **4 分钟**（相比全量重抓 6 分钟但要传几百 MB 正文）。
脚本按 ID 回填，不动 `content`，可安全重跑。

> ⚠️ 只给 `fetch-answers-api.mjs` 的 `INC` 加字段是**不够的**：
> 旧 `.state.json` 里每个分页都标了 `done`，重跑会直接跳过 → 新字段永远补不上
> （表现是「跑完了但 `answer_type` 全是 undefined」）。
> 脚本现在带 `STATE_VERSION`，检测到旧缓存会自动作废重抓并把旧缓存另存为 `.bak.json`。

## 2. 严选会被算法加权 —— 这是最要命的一条

question/303487786 实测：

| | 全题 | Top 20 | Top 100 |
|---|---|---|---|
| 严选条数 | 22（**0.56%**） | 9（**45%**） | 13（13%） |
| 占该段赞数 | — | — | **45.1%** |

**0.56% 的付费内容占了 Top100 赞数的 45.1%。**
按赞数排的榜单被推荐位加权的内容主导，直接引用「最高赞的回答是……」会把商业推广当成民意。

**处理方式：用 `--exclude-paid` 真的从数据里剔，不能只加个标签。**
`render-answers.mjs` 会同时重算母题聚合量 —— 否则 `themes.json` 里在全量上算好的
`count/votesSum/logSum` 仍会把被剔除内容的赞数算进来，等于没剔。

```bash
node "$S\render-answers.mjs" q<ID>-answers-full.json --exclude-paid --out q<ID>-汇总-去盐选.html
```

实测效果（全量判定口径）：

| | 原版 | 去盐选版 |
|---|---|---|
| Top 20 虚构占比 | 15/20 条，占赞数 **62.6%** | 9/20 条，占赞数 **27.6%** |
| Top 100 虚构占比 | 42/100 条，占赞数 **60.9%** | 32/100 条，占赞数 **28.7%** |
| 赞数合计 | 204,528 | 113,669 |

**剔除 22 条盐选（占全题 0.56%）就吃掉了 9 万赞**，头部虚构污染从 62.6% 降到 27.6%。

## 3. 虚构小说没有 API 标志，只能判内容

### 3.1 虚构率随篇幅陡增

question/303487786 **全量判定**（3898 条）后的分层：

| 篇幅 | 条数 | 虚构率 |
|---|---|---|
| 0–200 字 | 1747 | 1.4% |
| 200–500 字 | 374 | 7.0% |
| 500–1000 字 | 459 | 12.6% |
| 1000–3000 字 | 797 | 25.5% |
| 3000+ 字 | 521 | **60.1%** |

**只有长文值得重点判。** 200 字以下虚构率 1.4%，可以先不管。

> ⚠️ 这张表如果只靠「粗筛命中的样本」估，会**大幅高估中间层**：
> 早期用 283 条抽样版估出的是「200–500 字 0.0%、1000–3000 字 47.4%、3000+ 68.4%」，
> 全量实测分别是 7.0% / 25.5% / 60.1%。**分层比例只能用全量判定后的数，别用抽样。**

### 3.2 正则粗筛：能用来省钱，但不能用来定案

高精度信号（命中率低但几乎全对）：

```
【完结】【未完结慎入】【番外】【楔子】【序章】【未完待续】以下是正文
未经允许不得转载  本文原创  首发于  盐选
```

**分章编号是不可靠信号。** `chapters >= 6` 单独用假阳性极高 ——
「用 1. 2. 3. 分条列举真实经历」和「小说分章」在文本上几乎一样。
实测 1308 字、3399 字的真人真事被判成小说。只能搭配长度兜底（小说普遍 >5000 字）。

**并且正则必然漏**：`chapters` 的正则要求 `一.` 带点号，而 `一我换同桌了`（无点）抓不到。

### 3.3 用模型判（`classify-content-llm.mjs`）

```bash
# 全量判定（推荐）
node "$S\classify-content-llm.mjs" q<ID>-answers-full.json --all

# 抽样模式（只判「粗筛命中 + 随机抽样」，快但只能估比例）
node "$S\classify-content-llm.mjs" q<ID>-answers-full.json --sample 150
```

输出 `real` / `fiction` / `adapted` / `offtopic` 四类，写进 `q<ID>-content-kind.json`。
3898 条全量约 21 分钟（5~6s/批，每批 15 条，并发 5）。

### 3.4 ⚠️ 抽样能估比例，但保证不了头部正确

实测同一条数据，两种跑法结果差很大：

| | 抽样版（283 条判定） | **全量（3898 条判定）** |
|---|---|---|
| 小说占比 | **39.6%** | **15.0%** |
| 真实经历占比 | 44.9% | **63.2%** |
| 与问题无关 | 13.1% | **20.8%** |
| 「已判定真实」最高赞 | **39 赞** | **42036 赞** |

两处结论都是错的，而且方向相反：

1. **抽样判定集有偏** —— 抽样里塞了粗筛命中的高赞长文，而那些几乎都是小说，
   于是**虚构率高估 2.6 倍**（39.6% vs 15.0%）。分层比例同样被带偏：
   抽样版估的「1000–3000 字 47.4%」实测只有 25.5%。
   （外推公式本身没错，错的是输入。）
2. **抽样漏头部** —— 排第 1 的 42036 赞回答因为分章写法是 `一我换同桌了`（无点号）
   没被粗筛抓到，页面上显示「无标记」，读者会把小说当真实故事读。

**要让徽章真正可用，必须 `--all`。** 抽样模式只适合快速估个量级，
且**不得用于任何分层比例或头部陈述**。

## 4. 渲染层

`render-answers.mjs` 自动读取 `q<ID>-content-kind.json`，无需额外传参：

| 开关 | 作用 |
|---|---|
| `--exclude-paid` | 剔除盐选/严选付费内容（并重算母题聚合） |
| `--exclude-org` | 剔除机构号/广告主 |
| `--exclude-kind fiction,adapted` | 按判定结果剔除 |

页面自动获得：卡片徽章（`盐选/严选` / `小说` / `改编/虚构` / `真实经历` / `机构号`）、
工具栏筛选按钮、搜索可直接搜性质词。

全量判定后口径段会切成「全部 N 条已由模型逐条判定（无抽样、无外推）」，
否则会写「未判定的 N 条不代表是真实经历 —— 建议用 `--all` 全量判定后再引用本页数字」。

## 5. 报告里必须写的免责

**「真实经历」不等于内容为真。** 模型只能判断「叙述者是自述经历还是在编故事」，
无法核实事实本身。报告口径段必须写明这一点，否则等于替内容背书。

另外两个容易骗人的数字：

- **外推的虚构比例要标「外推」**。全量判定后应直接写实测值。
- **`offtopic`（灌水/抖机灵）规模要写出来**。实测占 20.8%（810 条），
  其中大量是「没有」「母胎solo」「已删除」这类，不写会让读者以为本来就没有。

## 6. 这套流程的坑

1. **模型会臆造不存在的回答 ID。** 实测出现过 `2144820996` 这种数据集里没有的 key。
   现在脚本只接受**本批内**的 ID，并在启动时清掉历史遗留的孤儿 key。
   仍要用 `verify-output.mjs` 复核，否则会出现「已判定 3899 / 回答 3898」这种数字。
2. **失败批写空值会让重跑永远跳过。** 续跑判断若用 `!state.perAnswer[id]`，
   而空值是 `{kind:''}` 这个 **truthy 对象** → 被当成「已完成」。
   现在统一以「`kind` 非空」作为完成判据，且失败时不写空值。
3. **模型输出的枚举值会被截断。** `offtopic` 被截成 `ofptopic` / `ofstof` / `of`
   （token 边界问题，实测 41 条中招）。已做前缀归一，`verify-output.mjs` 会复核合法性。
4. **批次会整批失败，需要拆。** 实测一条 2 字的「你」让整批 15 条都判不出来。
   现在批次失败自动对半拆分重试（最多 4 层），拆到单条即可出结果。
5. **未判完必须以非零退出码收尾。** 否则自动化会把半成品当成功 ——
   实测跑完 exit 0 但还有 108 条未判定，靠人看日志才发现。现在未判完 exit 2。

## 6.5 综述必须跟着剔除口径一起换

`--exclude-paid` 只改正文榜单和母题聚合，**综述是 summarize 阶段生成的**。
不改的话会出现「榜单已剔盐选、综述还在推荐被剔掉的付费小说」——

实测原版综述的「值得先读的故事」第 4 条是 `朝露何枯/2519赞`，
反查确认那是 22 条严选之一。

```bash
# 逐条摘要沿用缓存，只重建综述（约 10 秒）
node "$S\summarize-answers.mjs" q<ID>-answers-full.json --profile stories \
     --exclude-paid --only-digest --rebuild-digest
```

综述按口径存进同一个 `summaries.json` 的 `digests` 映射，
渲染时按开关自动选（`all|nokind` / `nopaid|nokind`）。
**key 只用纯口径，不要带模型前缀** —— 带前缀会让渲染端匹配失败后
静默回落到「最后生成的那份」，两个页面显示同一份综述。

另外综述要**校验结构完整**：实测模型返回过只含 `overview` 的残缺对象，
若直接采纳，页面会出现空的共识/分歧章节，且小标题回落成读书题的「共识要点」。

## 8. 已实测否决的优化（别重复尝试）

### ❌ 把「摘要」和「内容性质判定」合并成一次 LLM 遍历

**动机**：两件事都读同一条正文，分开跑要读两遍（827 批 + 265 批）。
合并后能省掉一整轮遍历，看起来是白捡的 5 分钟。

**实测否决**。同一份 40 条标注样本上的 A/B：

| 方案 | kind 准确率 |
|---|---|
| 独立判定（`classify-content-llm.mjs --all`） | **97.5%**（39/40） |
| 合并判定（`summarize-answers.mjs --with-kind`） | **67.9%**（19/28） |

**差 29.6 个百分点**，8 条不一致全部是「把小说/改编误判成真实经历」。
摘要长度没受影响（中位 48 vs 49 字），**只有判定质量崩了**。

原因：模型的主任务变成「写摘要」后，会把一切都当成「要总结的故事」，
不再做「这是真的还是编的」这种批判性判断。**任务合并会改变模型的判断姿态。**

代码里保留了这个开关，但注释写明不推荐、默认关闭 —— 留着是为了让下一个想省这一步的人
先看到这个数字，而不是自己再踩一遍。

### ✅ 保留：抽样模式（但要标明用途）

`--sample N` 仍然有用，只是**不能用于分层比例或头部陈述**（见第 3.4 节）。
它的正确用途是：跑全量前先快速估个量级、验证提示词是否可用。

## 9. 判断流程（照做）

```
故事征集题？
├─ 是 → 抓取时 include= 已含 answer_type（新产物无需补抓）
│     → classify-content-llm.mjs --all          ← 头部排序会被虚构主导，别用抽样
│         （不要用 summarize --with-kind 合并，实测准确率 68% vs 98%）
│     → 若要出「去盐选版」：
│         summarize-answers.mjs --exclude-paid --only-digest --rebuild-digest
│         render-answers.mjs --exclude-paid --out q<ID>-汇总-去盐选.html
│     → render-answers.mjs                       ← 自动出徽章 + 筛选
│     → verify-output.mjs --html q<ID>-汇总.html ← 退出码 0 才算跑完
│     → 报告里写：虚构条数与占比 + 「真实经历≠内容为真」+ offtopic 规模
└─ 否 → 常规流水线
```

## 10. 怎么知道自己改得好不好

`eval-extraction.mjs` 是唯一的客观标准 —— 改提示词、换模型、调阈值之前先跑它。

```bash
# ① 生成分层样本（一半高赞、一半随机，避免只看到头部）
node "$S\eval-extraction.mjs" q<ID>-answers-full.json --make-sample 40
# ② 人工填 expected，然后评估
node "$S\eval-extraction.mjs" q<ID>-answers-full.json --check q<ID>-eval-sample.json
```

输出总体准确率、逐类精确率/召回率/F1、混淆矩阵，以及**错例明细**（改提示词就靠这个）。

**本机实测基线**（40 条分层样本，question/303487786）：

| 类别 | 精确率 | 召回率 | F1 |
|---|---|---|---|
| real | 90.0% | 100.0% | 94.7% |
| fiction | 100.0% | 90.9% | 95.2% |
| adapted | 100.0% | 100.0% | 100.0% |
| offtopic | 100.0% | 100.0% | 100.0% |
| **总体** | | | **97.5%**（39/40） |

> ⚠️ **这个数字要打折看**：标注是 AI 做的，且与预测模型同族 ——
> 属于「一致性检查」，不是独立人工标注，会系统性高估真实准确率。
> 唯一错例：一条 5510 字、有名有姓（江易/褚薇）的小说被判成 real。
> 要得到可信数字，必须由人来标。
