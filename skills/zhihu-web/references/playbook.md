# 知乎实体抽取实战手册

> 这份文档记录的是**踩过的坑和验证过的判断**，不是理想状态下的用法。
> 写给下一个接手这件事的 AI 或人。

---

## 0. 先判断你在做什么

拿到一个知乎问题，先分清是「检索」还是「量化」。

| 你要什么 | 走哪条路 |
|---|---|
| 找内容、找观点、看某人写了什么 | 官方 zhihu CLI |
| 要赞数、发布时间、评论数、排序 | Panerelay（登录态通道） |
| 要把 N 条回答里的实体抽出来统计 | 本文档的完整流程 |

判断标准就一条：**答案里要不要出现数字**。

## 1. 两条数据通道，各有各的坑

### 官方开放平台 CLI

- `question answers` 只返回 4 个字段（ContentType / ContentToken / Url / Summary）
- **没有赞数、没有发布时间、没有排序参数**
- `search zhihu` 单次最多 10 条且 `HasMore` 恒 false（无分页）
- `Paging.Totals` 实测从不返回，别拿它推断总数
- 输出是 UTF-8，**PowerShell 读必乱码**，一律用 Node 处理

完整踩坑记录：`~/.config/opencode/notes/zhihu-cli.md`

### Panerelay（复用本机 Edge 登录态）

**它有一个致命前提：扩展 manifest 必须有静态 `host_permissions`。**

```
没有 host 授权 → chrome.cookies.getAll() 返回空数组
             → 拿空 Cookie 表去注入
             → 服务端一律 401「身份未经过验证」
```

这个报错极具误导性：看起来像知乎风控、像没登录、像浏览器兼容性。**实际是本地 manifest 少一个字段。**
本机已修补（源码 + 构建产物都改了）。换扩展目录或 rebuild 后**必须复查这一行还在**。

验证是否真的修好，看底层请求返回里的 `attachedCookieCount`：

```bash
panerelay fetch "https://www.zhihu.com/api/v3/feed/topstory/hot-lists/total?limit=2" --response json
```

> `whoami` 通过 **不代表** Cookie 注入成功。它只验证桥接连通。
> 我在「桥接通了但 Cookie 是空的」这个假象上绕了二十多步。

其他必知的：

- `question` 命令收**数字 ID**，不收 URL
- 输出是**顶层 JSON 数组**，不是带 `items` 的对象
- Node 里必须 `spawnSync('cmd.exe', ['/c','panerelay',...])`；直接 spawn `.cmd` **静默失败**（exit 0、stdout 空、无报错）
- 必须用桌面「Edge (Panerelay)」快捷方式启动 Edge；普通图标启动扩展不加载

## 2. 最重要的一条：`question` 的 content 是截断的

```bash
panerelay zhihu question <id> --limit 5 --json
# content 字段：最短 0、中位 36、最长 200 字符
```

**中位数只有 36 字符。** 用它做实体抽取会漏掉绝大部分内容。

必须逐条取全文：

```bash
panerelay zhihu answer-detail <回答ID> --max-content 0 --json
```

`--max-content 0` 才是「全部」，不是「不要内容」。

实测对比（question/28193957，380 条回答）：

| 来源 | 正文总量 |
|---|---|
| `question` 的 content | 25,829 字（截断后） |
| `answer-detail --max-content 0` | 98,556 字 |

**差 3.8 倍。** 任何实体抽取都必须用后者。

## 3. 抓取：并发到 3 就是上限

实测（question/28193957，380 条）：

| 配置 | 速率 | 结果 |
|---|---|---|
| 串行 + 350ms sleep | 0.83 条/秒 | 519 条要 10 分 18 秒 |
| **并发 3 + 60ms sleep** | **1.3 条/秒** | **380 条 5 分 06 秒** |
| 并发 6 + 40ms | 1.3 条/秒 | 无增益 |
| 并发 10 + 40ms | 1.2 条/秒 | 反而变慢 |

**并发超过 3 没有收益。** 瓶颈不在浏览器端，而在每次调用要起一个 Node 进程（~500ms 启动开销）。

也**没有观察到 DNR session 规则串扰**（并发 10 时 fail 仍为 0）。但收益也没了，没必要冒险。

```bash
node tools/fetch-answers.mjs <问题ID> --concurrency 3 --sleep 60
```

脚本自带断点续跑，中断后重跑同一命令即可。

## 4. 实体抽取：三层结构 + 噪音必须显式过滤

通用结构（`extract-entities.mjs` + `presets/*.json`）：

```
L1 高精度规则    行内代码 / 书名号 / 明确格式
L2 次优标记      弯引号 / 直角引号
L3 精选词典      补裸实体
L0 噪音过滤      贯穿三层
```

### 实测教训一：中文弯引号不是书名

`对中国"当下"有深刻见解` —— 弯引号层会命中「当下」，当成书名收进去。

中文大量使用 `“”` 做强调。书名极少含虚词，据此过滤：

```json
"rejectChars": "的了是在和就都而及与或很你我他她它这那有没不..."
```

过滤前 772 个「书名」，过滤后 555，「当下」这类误报清零。

### 实测教训二：《》里面装的也未必是书名

知乎人常写《》引概念：

> 《三农问题》《蚁族》《技术赋权》《卖淫交易》《社会》

加 `contextGuard`：书名号附近 30 字符内必须出现「著/作者/推荐/读/看/这本书」等书籍语境词。

**效果：砍掉 240 个，其中大部分确实是概念而非书。**

但守卫**也会误伤真书**（《伤逝》《晚清七十年》《中国制度史》）。
所以：**不要静默丢弃** —— 把被砍掉的记录到 `extraction.contextGuardDroppedSample`，
在报告的「数据口径」里写明。口径要可查，不能让读者以为「知乎只提到 239 本」。

### 实测教训三：词典层会混入作者名和宽泛英文词

我第一版词典里塞了「吴思」「余华」「黄仁宇」（作者不是书）和
「China」「Dying」「Guns」（匹配任意英文语境）。结果「China」拿到 10 次提及。

**词典只放实体本身。** 宁可少召回，不要把作者名和通用词放进去。

### 实测教训四：`contextGuard` 会误伤，别当银弹

砍掉 240 个里混着真书。如果你的场景里《》基本都指书（而非引概念），
**直接关掉 contextGuard**，让噪音进列表但标注来源层级，比误删真书好。

```json
// 删掉 contextGuard 这一行即可关闭
```

### 实测教训五：全文比摘要多 5 倍，结论也会变

同一个问题（question/24590883），两种取法结果差很多：

| 取法 | 正文字数 | 抽出实体 |
|---|---|---|
| `question` 的 content（截断） | 25,829 | 136 |
| `answer-detail --max-content 0` | **1,139,266** | **196** |

字数差 44 倍，实体数差 60 个。**用摘要做的抽取，结论是残缺的。**

顺带一个观察：词典里的 `logging`（Python 标准库）拿到 26 次提及，排在 TOP 12。
它是标准库不是「相见恨晚」的第三方库 —— **标准库要不要算，取决于问题问的是什么，
预设应该据此调词典。**

## 5. 报告设计

两个反复出现的排版错误：

**① 嵌套表格塞在单元格里会撑破布局。**
溯源明细不要用 `<td>` 里再套 `<table>`。改成 grid 行 + 展开时插入整行面板。

**② 数字列没有视觉权重。**
「89」和「2」并列时读者无法比较。用进度条 + 对数刻度，让数量级差异可见。

其他：

- 跟随系统的明暗主题（`prefers-color-scheme`），别只做一种
- 数值列一律 `font-variant-numeric: tabular-nums`
- grid 子项要加 `min-width: 0`，否则内容撑破容器
- 进度条内部用 grid 轨道（`minmax(0,1fr) auto`），用 flex 会溢出压到相邻列

## 6. 一条命令跑通

```bash
node tools/pipeline.mjs <问题ID> --preset <预设名>
```

做完了会自己检查桥接、打印失败原因。产物：

```
q<ID>-answers-full.json       全部回答：全文 + 赞数 + 时间 + 评论
q<ID>-entities.json           规范化实体 + 抽取统计（含被过滤的内容）
q<ID>-<问题标题>.html/.md     报告
```

复用已有抓取结果（跳过 5-7 分钟）：

```bash
node tools/pipeline.mjs <问题ID> --preset <预设名> --skip-fetch
```

换实体类型：**写一个 `presets/xxx.json`，不用改代码。** 字段说明见 `presets/_README.md`。

## 7. 报告里必须交代的口径

这几点每次都会被追问，所以写死：

1. **正文是全文不是摘要** —— 避免读者以为数据不全
2. **样本量差值要说明原因** —— 「官方 CLI 542 条，Panerelay 519 条，差的 23 条是已删除或已隐藏」
3. **「最高赞」是代理指标** —— 它是「提到该实体的回答里赞数最高那条」的赞数，不等于实体本身热度
4. **噪音过滤的规模要写** —— 「滤掉 132 条疑似非书名」，而不是让人以为本来就没那么多
5. **缺失值标出来，不要用 0 冒充**
6. **每条结论挂原文链接**

## 8. 我踩过并修掉的实现级坑

留给下一个人省时间：

- **`import.meta.url` 的 pathname 带 URL 编码**（`%20`）。用 `fileURLToPath(import.meta.url)`。
- **JSON 文件里的正则必须是字符串**（JSON 存不了字面量 RegExp）。`new RegExp(rule.re.source)` 会得到
  `undefined` → 空正则 → 静默 0 命中。要判断 `typeof rule.re === 'string'`。
- **PowerShell 的 `Set-Content -Encoding UTF8` 会写 BOM**，Node `JSON.parse` 直接报错。
  读取时 `.replace(/^\uFEFF/, '')`。
- **验证脚本里硬编码路径 = 定时炸弹。** 我有个临时脚本 SRC 写死，结果误用时把 A 报告覆盖成了 B 的内容。
  所有脚本一律参数化。
- **字符类重复包括号会静默误杀一切。** 写 `"requireChars": "[A-Za-z0-9]"`，代码又拼成
  `new RegExp("[" + s + "]")` → `[[A-Za-z0-9]]`，语义变成「含 `[` 或字母或数字，**且后面必须紧跟字面量 `]`**」。
  后果是 2068 条命中全部被拒、实体数为 0，而控制台只显示「过滤 2068 条」——
  **看起来像过滤太狠，其实是配置解析错了**。
  代码现在容忍两种写法（`/^[[].*[\]]$/.test(s) ? s : '['+s+']'`），但写预设时注意语义。
- **抽取出 0 实体时，先怀疑规则没生效，不是过滤太狠。** 看 `layerHits` 是否为空：
  为空说明正则层就没命中（`rule.re` 当 RegExp 取 `.source` 会得到 `undefined` → 空正则 → 静默 0 命中）；
  非空但实体为 0 才是过滤器问题。
- **`fmtDate` 判断要先 `Date.parse`**，否则空值会渲染成 `Invalid Date`。
- **文件写入的反引号可能被转成全角句号**，写完模板字符串先验证能解析。

## 9. 还没做的

- **给上游提 PR**：`optional_host_permissions` 在侧载场景下无人授权，导致 Cookie 表为空。
  这是真 bug，作者一看就懂。`api.github.com` 和 `codeload.github.com` 在本机可通。
- **并发上限还没到理论值**：瓶颈在每次调用的进程启动。如果 Panerelay 支持批量或长连接，能再快一个量级。
- **抽取质量没有量化评估**：目前靠人工看 TOP 20 的溯源。应该做一套标注集算精确率/召回率。
