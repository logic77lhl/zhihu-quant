# 知乎汇总流水线 v2（2026-10 实测）

> 这份文档记录的是**已跑通并验证过**的「把一个知乎问题做成一页可读报告」的全流程，
> 包含每一步踩过的坑、判断依据和实测数字。
> 脚本**内含在 skill 里**：`skills/zhihu-web/scripts/`（下称 `$SCRIPTS`）。换机部署见 `setup.md`。
> **产物目录不在脚本目录**：按 `$ZHIHU_QUANT_OUT` → `config.json` 的 `outDir` → `~/Documents/zhihu-quant`
> 顺序解析。找不到产物先查这两个，别急着重抓。
> 只做实体统计的老流程见 `playbook.md`。

---

## 0. 先判断你在做什么

| 你要什么 | 走哪条路 |
|---|---|
| 把 N 条回答做成一页能读完的东西 | **本文档** |
| 统计某类实体（库/书/公司）且回答数 <1000 | `playbook.md` 的正则管线 |
| 要赞数、发布时间、评论数、排序 | Panerelay（登录态通道），没有例外 |

判断标准还是那条：**答案里要不要出现数字**。

## 1. 全流程命令

```bash
$SCRIPTS = "$env:USERPROFILE\.config\opencode\skills\zhihu-web\scripts"
node "$SCRIPTS\fetch-answers-api.mjs" <问题ID>          # ① 全量全文（>1000 条也能拿全）
node "$SCRIPTS\summarize-answers.mjs" q<ID>-answers-full.json        # ② 逐条摘要 + 全局综述
node "$SCRIPTS\extract-themes-llm.mjs" q<ID>-answers-full.json      # ③ 观点聚类（讨论题）
node "$SCRIPTS\extract-books-llm.mjs" q<ID>-answers-full.json       # ④ 抽书单（书单题）—— ③④ 二选一或都跑
node "$SCRIPTS\render-answers.mjs" q<ID>-answers-full.json          # ⑤ 渲染 q<ID>-汇总.html
node "$SCRIPTS\build-index.mjs"                                  # ⑥（可选）刷新目录 index.html
```

> ⚠️ 迁移前的旧路径 `$D\tools\` 已全部改为 `$SCRIPTS\`。
> 别处再看到 `$D\tools\` 就是历史文档，以本节为准。

**故事征集题在 ② 之后额外插两步**（内容性质判定，见 [`content-kind.md`](./content-kind.md)）：

```bash
node "$SCRIPTS\classify-content-llm.mjs" q<ID>-answers-full.json --all    # ②' 逐条判真实/虚构/无关
node "$SCRIPTS\verify-output.mjs"        q<ID>-answers-full.json          # ②'' 校验产物（退出码 0 = 可用）
```

跳过这两步的代价是实测过的：按赞数排的 Top20 里 **62.6% 的赞数来自虚构内容**，
第 1 名（49070 赞）是盐选付费小说。`classify-content-llm.mjs` 的 `--all` 不能省 ——
抽样模式会把虚构率高估 2.6 倍，且保证不了头部条目标注正确。

### 「有哪些……故事」类征集题要加 `--profile stories`

**默认提示词是给读书/观点题写的，直接套到故事征集题上会产出垃圾**：
综述里问「回答分为哪几派」「入门阅读顺序建议（带书名）」，
标签体系要求「区分原因解释与解决方案」—— 对「有哪些平淡却心酸的暗恋故事？」
这种题全部答非所问。

```bash
node "$SCRIPTS\summarize-answers.mjs"  q<ID>-answers-full.json --profile stories
node "$SCRIPTS\extract-themes-llm.mjs" q<ID>-answers-full.json --profile stories
```

`stories` 档的三处变化：

| 位置 | 默认 | stories |
|---|---|---|
| 逐条摘要 | 「推荐了什么 / 核心主张」 | 「谁与谁、因为什么事、最后怎么样，那个心酸的点」 |
| 综述字段 | `consensus` 共识要点 / `disputes` 分歧 / `readingPath` **入门阅读顺序（书名）** | 反复出现的母题 / 结局的几种形态 / **值得先读的故事（作者+赞数，不是书名）** |
| 标签体系 | 核心观点、区分「原因 vs 方案」 | **关系原型 + 结局形态**（如「多年暗恋不敢说」「重逢已各自成家」），禁止「青春」「遗憾」这类无区分度的词 |

综述会多出一个 `labels` 字段覆盖三节的标题，`render-answers.mjs` 优先用它，
没有才回落到读书题默认值。

`render-answers.mjs` 会**自动识别**故事征集题（无书单产物但有标签），
把页面上的「观点排行 / 主张」全换成「故事母题排行 / 故事」，`build-index.mjs` 同理，
不需要额外传参。

实测（question/1937248651517863299，3707 条回答）：

| 阶段 | 耗时 |
|---|---|
| ① 全量抓取 | 4.3 分 |
| ② 摘要 | 2.9 分 |
| ③ 观点 | 1.7 分 |
| ④ 书单 | 2.2 分 |
| ⑤ 渲染 | <0.1 分 |

抓取是**唯一没被优化掉的**，372 次请求每次起一个 Node 进程（~500ms 启动开销）。

## 2. 抓全量：绕开 `--limit 1000` 的天花板

### 坑 1：`question` 命令最多 1000 条

`panerelay zhihu question <id> --limit 1000` **单次上限 1000，且该命令没有分页参数**。
question/1937248651517863299 有 3707 条，即使跑两种排序合并也只拿到 **1597 条**。
`playbook.md` 里「两种排序合并」的技巧在有分页能力之后就不必要了
（2026-10-16 进一步实测：分页下 `default` 是 `created` 的超集，单排序即可，见坑 5）。

### 坑 2：`&` 会被 cmd.exe 当命令分隔符

```js
// ❌ URL 被截断成 ...answers?limit=20，后面的 &offset=... 被 cmd 当成命令执行
spawnSync('cmd.exe', ['/c','panerelay','fetch', url, '--response','json'])
// ✅ 每个 --query 是独立参数，不经过 & 分隔
spawnSync('cmd.exe', ['/c','panerelay','fetch', BASE_URL, '--query','limit:20', '--query','offset:0', ...])
```

实测报错形态：panerelay 收到 `"https://...answers?limit=20`，然后 cmd 报
`'offset' 不是内部或外部命令`。

### 坑 3：分页接口的 `limit` 上限是 20

试过 50 / 100，**返回 0 条且无 error**（不报错，只是空）。别以为调大能省请求。

### 坑 4：分页接口返回的是全文 HTML，不是截断摘要

```
GET /api/v4/questions/<qid>/answers
  ?limit=20&offset=<n>&sort_by=default
  &include=data[*].content,voteup_count,comment_count,created_time,updated_time,author.name,question.title
```

`question` 命令的 `content` 被截断到 200 字符，但**这个端点给的是全文 HTML**。
本地去标签后与 `answer-detail --max-content 0` 的纯文本**逐字一致**（实测 6/6，
含 3792 字长文、`content_need_truncated=false`）。

于是：**186 次分页请求 = 全部 3707 条全文**，而不是 3707 次逐条抓取。
**4.3 分钟 vs 约 47 分钟。**

### 坑 5：排序差异 —— created 只是 default 的子集（2026-10-16 修正）

旧结论「两遍都跑再按 id 合并」不再需要，**单排序 `default` 就是超集**：

- A/B 实测（question/650705759）：`default` 703 条 ⊇ `created` 659 条，仅 created 有的 **0 条**；
  两排序 `totals` 相同（710）；小问题 38 = 38，差集 0
- 旧说法「集合确实不同」来自 `question --limit 1000` 的**截断**场景（`playbook.md` 年代的技巧），
  分页翻到底后不存在这种差异
- `fetch-answers-api.mjs` 默认：default 全量 + created 首屏覆盖检查（不通过才补抓 created）；
  `--sorts both` 保留旧的双排序全抓

### 坑 6：能拿到哪些字段，别猜

| 字段 | 能否拿到 | 怎么拿 |
|---|---|---|
| 赞同数 / 评论数 / 发布时间 / 更新时间 | ✅ | 默认返回 |
| 正文全文 | ✅ | `include=data[*].content` |
| **感谢数 `thanks_count`** | ⚠️ | **必须显式写进 `include=`**，漏了就静默不返回 |
| **收藏数** | ❌ | **接口不暴露**。加 `favorite_count` 会被静默丢弃（无报错） |

所以标准 include 是：

```
data[*].content,voteup_count,comment_count,created_time,updated_time,thanks_count,author.name,question.title
```

`answer-detail` 返回的字段更少（只有 `votes/comments/created_at/updated_at/content` 等），
**要感谢数就必须走列表接口**。

用户要「收藏数」时直接说拿不到，不要反复试参数名 —— 试过
`favorite_count` / `reaction_count` / `reshipment_count` / `data[*]` 全宽包含，都不返回。

### 故事征集题：include 必须带上三个标志字段

`answer_type`（是否盐选/严选付费）、`author.is_advertiser`、`author.user_type`
**默认不返回**。`fetch-answers-api.mjs` 的 `include=` 已包含它们。

**实测验证**（2026-10-15，question/491790104）：

| 检查 | 结果 |
|---|---|
| 全新抓取 `answer_type` 覆盖 | 205/205 ✓ |
| `author_type` / `is_advertiser` 覆盖 | 205/205 ✓ |
| `state.version` | 2 ✓ |

在补字段之前抓的旧产物只能用 `enrich-flags.mjs` 事后补（396 页约 4 分钟）。

它们决定了能不能剔除被推荐位加权的付费内容 —— 实测某题全题 0.56% 的严选内容
占了 Top100 赞数的 45.1%。详见 [`content-kind.md`](./content-kind.md)。

> ⚠️ 只改 `INC` 是不够的：旧 `.state.json` 里分页都标了 `done`，重跑会跳过，
> 新字段永远补不上（表现是「跑完了但 `answer_type` 全是 undefined」）。
>
> 脚本带 `STATE_VERSION`，检测到旧缓存自动作废重抓，并把旧缓存另存为 `.state.v1.bak.json`。
> **实测验证**：模拟旧缓存（205 条缺字段 + 删掉 `version`）后重跑，
> 正确打印「检测到旧版缓存，作废重抓」，备份生成，重抓后 205/205 字段齐全。

### 收尾口径

平台 `paging.totals` 说 3707，实收 **3667**，差 40 条。
已删除/已折叠的回答不再返回，**这是正常差值，要在报告里写明**，别当成漏抓。

### 去标签要对齐 `answer-detail`

去标签后必须与 `answer-detail` 一致（汇总页里混着两种格式的正文，后续哈希/搜索会出问题）。
`fetch-answers-api.mjs` 里的 `stripHtml()` 处理了 `figure/img/br/p/li` 与常见实体。

## 3. 书名抽取：正则的召回是坏的，别用它做排行

### 实测数据（question/491790104，204 条回答）

正则（`extract-entities.mjs --preset books`，只认 `《》` + 弯引号 + 词典）**漏掉最高频的书**：

| 书 | 正文提到 | 赞和 | 正则收录？ |
|---|---|---|---|
| 转型中的地方政府 | 15 条 | 11,334 | **否** |
| 以利为利 | 14 条 | 11,286 | **否** |
| 当代中国政府与政治 | 8 条 | 9,037 | **否** |
| 分析与思考 | 9 条 | 3,420 | **否** |

原因是这些书大多写成**裸书名**（不带书名号）。所以正则版书单实际是
「谁恰好带了书名号」的筛选结果，不是被推荐的书。

### LLM 抽取能解决什么

`extract-books-llm.mjs` 逐批读全文，让模型输出 `{title, author, polarity}`：

- 能抓裸书名
- 能合并同书异名（「周雪光的中国国家治理的制度逻辑」→「中国国家治理的制度逻辑」）
- 能区分 **rec 推荐 / avoid 劝退 / mention 顺带提到**
- 修正后该题 Top8 与 AI 综述里的共识完全对得上（修正前对不上，因为漏了那几本）

### 一句话回答就是一张选票

正文只有「大国大城」四个字的回答，本质是一次推荐。
规则：**正文 <40 字时，`mention` 提升为 `rec`**。
实测该题让《大国大城》推荐数 9→13、《以利为利》9→12。

但**抽书名只靠 LLM 不行、只靠正则也不行**，实务上：LLM 抽名单 + `paging.totals` 对账。

## 4. 排行口径：这 6 条都是踩出来的

| 规则 | 理由 |
|---|---|
| **问题本体剔除** | 问题里问的那本书（《置身事内》）会被大量低赞回答顺口提及，排第一是把「问题本身」当「推荐结果」。均赞 298 vs 同类 1488，明显不是一回事 |
| **热度只算推荐，不算提及** | 否则被大量顺口提到的书会挤掉真正被推荐的。实测《射雕英雄传》（推荐 5 / 提及 33）按提及排序排第 1，只算推荐后掉出前 15 |
| **用阻尼热度 `Σlog10(1+赞)`** | 纯提及数把 2 赞和 3298 赞等权；纯赞数和又被单条超高赞回答拉偏（一条 3298 赞回答顺带提到的书全部并列）。取 log 是两者折中 |
| **≥2 人推荐才进榜** | 抽 285 个实体里 261 个只被 1 条回答提到，排行里塞满一次性提及没有意义 |
| **提供多口径切换** | 「推荐热度 / 推荐人数 / 推荐赞数和」结果差别很大，让读者自己切，不要替他选 |
| **标注「最高赞」是代理指标** | 那是「提到该书的回答里赞数最高那条」的赞数，不等于书本身热度 |

观点标签没有极性问题，但仍要**≥2 原则**和**未打标条数披露**（见下）。

## 5. 观点讨论题：正则和书单都不适用

「为什么我一年读三百本书没长进」这种题，抽书名和抽实体都没意义。做两步：

### A. 归纳标签体系（一次调用）

取**高赞回答的要点**（不是全文，省 token），让模型归纳 12~16 个互斥标签。
提示词里必须写死这几条要求，否则标签会变得没法用：

- `name` ≤14 字，**禁止「读书方法」「个人成长」「心态问题」这类笼统词**
- 标签要能区分「原因解释」和「解决方案」
- 只输出 JSON

### B. 逐条打标

每条回答选 1~3 个；**判为「简短赞同/调侃/无实质观点」的给空数组**，不进入排行。
空数组是正常结果，不要为了提高覆盖率硬凑。

### 实测效果

question/1937248651517863299 抽出 16 类，覆盖 3136/3667 条：

```
知识须用于实践 / 读太快根本没吸收 / 慢读精读反复读 / 读多不如读懂 /
缺输出则无内化 / 选书不如所选方向 / 先定目标再选书 / 量变终会引发质变 /
读专业书才有长进 / 读闲书本来就没用 / 知行之别在行动力 / 读原著胜过读解读 /
用战术勤奋掩盖懒惰 / 读书先祛魅当工具 / 阅历不够读也白读 / 费曼式教学才有效
```

**标签体系是每个问题重新归纳的，换模型结论就会变**——这是正常的，不是 bug。
换模型后 A/B 实测：标签名几乎全不一样（正常），但覆盖量与打标质量相当。

## 6. 模型与 reasoning（本地网关）

四个 LLM 脚本（含 `classify-content-llm`）默认 **`--model auto`** + `reasoning_effort: "none"`
（`opencode.jsonc` 里标注 x0.00，免费）。用 `--model` / `--effort` 覆盖。

**auto 是什么、为什么**（2026-10-16）：auto 开局探测模型链
（默认 `global:deepseek-v4.1-flash,cn:deepseek-v4.1-flash`）挑第一个可用的，结果缓存 10 分钟。
起因：上游限额期间 `global:` 返回 503，而每批失败重试是「4 次退避 + 二分拆批再各重试一遍」——
单批几十秒、整轮几分钟空转零产出；同一时刻 `cn:` 正常（38 条 / 12 批 / 20 秒）。
显式 `--model <id>` 时不探测，与旧行为完全一致。
`auto` 模式下换上游（global→cn）**不作废 state 缓存**，实际模型记录在产物 `resolvedModel` 字段。
批次命中 429/5xx 会等 5 秒**收尾重试**一轮（瞬时抖动重试即过，不必手工补跑）。

### 「只输出 JSON」必须同时写在 user 消息结尾（2026-10-29 实测）

本机网关会注入一层对话式人格：**只把 JSON 要求写在 system 里，模型会把 user 内容当成「用户在跟我聊」，
回一段散文**，脚本报 `非 JSON 数组: 你的观点基本成立，但可以补充几点…`。

对照实测（同一份数据、同一批模型）：

| 脚本 | JSON 要求写在哪 | 结果 |
|---|---|---|
| `summarize-answers.mjs` | system + **user 结尾再写一遍**「请输出 JSON 数组，形如 [...]，覆盖上面每一条 id」 | 44/44 批通过 |
| `extract-themes-llm.mjs` | 只写在 system | 13/13 批全挂（deepseek / glm / kimi 都一样） |
| `summarize-answers.mjs` 的综述 | 只写在 system | 两个模型都返回 Markdown 长文，`consensus/readingPath` 缺失 |

修法：在 user 消息结尾追加一句显式格式要求（`tagBatch` / 综述 / 标签归纳三处都一样）。
`render-answers.mjs` 的 `--opinion` / `--reviewed` 与本条无关，见 §7。

### 观点题的标签体系别硬信模型

同一题（question/420024656，323 条）上，模型把「顺带提到 C++」当成「高频与执行层用 C++」，
164/315 条被打上该标签，连 5509 赞那条讲「语言押注」的也被标成 T1/T2；换 deepseek / glm / kimi
都只是换一种错法（kimi 全打 T4）。**结论：标签归纳 + 逐条打标这类映射任务，模型在本机网关上不可靠。**
可行做法是人工复核头部（有赞回答 159 条）后写回 `perAnswer`，页面上如实标 `--reviewed`。

### 哪些参数真能关 reasoning

只有两个生效，其余**静默失效**：

| 参数 | deepseek-v4.1-flash 的 reasoning |
|---|---|
| `reasoning_effort: "none"` | **0 字** ✅ 1.1s（原 2.0s） |
| `thinking: {type:"disabled"}` | **0 字** ✅ 1.4s |
| `reasoning_effort: "minimal"` | 237 字 ❌ 没降 |
| `enable_thinking: false` | 182 字 ❌ 忽略 |
| `thinking: false` | 185 字 ❌ 忽略 |
| `reasoning: false` | 254 字 ❌ 忽略 |

两个反直觉的坑：

- `gpt-6-luna` 加这些参数 → **HTTP 200 但 content=0、tokens 0/0**，静默返回空
- `kimi-k2.6` 加 `reasoning_effort:"minimal"` 反而**打开**思考（591 字 / 8s），基线本来是 0

三个脚本都有兜底：带 `reasoning_effort` 拿到空返回时，自动去掉该参数重试一次。

### 慢的不是 reasoning，是模型

同一批 20 条回答（约 6300 字）：

| 配置 | 耗时/批 | 价格 |
|---|---|---|
| `global:glm-5.3-flash` | 14.2 – 15.9s | x0.06 |
| `global:deepseek-v4.1-flash` + `none` | **4.8 – 5.8s** | **x0.00** |

**2.7 倍**，摘要质量逐条比对无差异。glm 的 reasoning 实测≈0，瓶颈是模型本身。

### 换模型必须作废旧缓存

state 文件里存 `modelTag = MODEL + '|' + EFFORT`，**严格比对**（不是 `if (state.modelTag && ...)`，
否则旧 state 没有这个字段时不会作废）。不一致就清空重跑。
不这么做就会拿旧模型的结果混进新模型的产物。

### 并发上限约 5（LLM 网关）

实测并发 3→8→12，吞吐只提升 1.0~1.09x；而**并发 12 时 15 个批次只成功 6 个**。
加并发换来的是失败而不是速度。别调高。

> ⚠️ 注意这条**只适用于本地 LLM 网关**。抓取那条通道的「并发上限 3」结论已被修正，
> 见下方「抓取通道的并发：原结论要修正」。

### 抓取通道的并发：原结论要修正

> ⛔ **先说规则：不要为了验证这一节去实测并发边界。**
> 上一个 AI 就是这么干的 —— 约 147 次请求、同一 endpoint、零间隔、并发拉到 10。
> 它当时以为这导致了限流并写进了文档，**但那个归因是错的**（实测是 `code 10003` 缺签名，
> 换个没请求过的 endpoint 也 403，而 `/api/v4/me` 返回 200）。
> 仍然不要压测的理由不是「会封号」，而是**会浪费配额、产生假数据、浪费一整轮诊断**。
> 详见 `SKILL.md` 顶部的「两条必须分清的 403」。

**原结论**：「并发 3→12 吞吐只提升 1.0~1.09x，瓶颈在每次调用起 Node 进程（约 500ms），
且高并发会让 DNR 串扰。」

**实测拆解单次调用的耗时构成**（2026-10-15，用**单次调用**拆解，不是并发压测）：

| 环节 | 耗时 |
|---|---|
| 裸 node 启动 | 63 ms |
| + 加载 panerelay CLI 入口 | +76 ms |
| + 网络请求与序列化 | +126 ms |
| **单次总计** | **264 ms** |

发现两个问题：

**① 瓶颈不是进程启动，是 `spawnSync` 阻塞事件循环。**
`panerelay-run.mjs` 用的是 `spawnSync`（同步阻塞），所以 `fetch-answers-api.mjs` 里
那 3 个 async worker **实际是轮流执行的** —— 每个 `spawnSync` 都会卡住整个事件循环，
「并发 3」名不副实。这解释了为什么调高并发完全没收益：**它压根没并发**。

**② 那次 1.0~1.09x 的数据可能被 403 污染。**
当时测并发时接口已经在返回 403，而 **403 响应返回得很快** ——
于是「失败请求」被当成「快速响应」计入了吞吐。
**那次测量整体作废**，既不能用来支持「并发无用」，也不能用来支持「并发有用」。

**因此**：

- 「改成异步 `spawn` 能提速」是一个**有代码依据但尚未验证的假设**。
  按耗时拆解推算 264ms → 126ms（约 2.1x），但**没有干净的实测数据支撑**。
- **要验证它，必须用单次调用拆解耗时，不要用「并发跑 N 页看总耗时」** ——
  后者就是上次翻车的方式。
- **不要**在没有干净数据的情况下调高并发默认值。

**性能脚本的正确写法**：

```js
const j = JSON.parse(out);
if (j.status !== 200) throw new Error('失败，本次计时作废');   // 403 会被当成「快」
```

### 输出被 max_tokens 截断的批次，重跑永远不会自愈

`parseJsonLoose` 失败报的是 `非 JSON 数组`，看起来像模型不听话，
实际上是 **JSON 数组没闭合**——模型写到一半撞上 `max_tokens` 上限被切断。

**为什么重跑救不回来**：分批是按固定预算切的，同一批超长内容每次切法完全一样，
所以重跑会以同样方式失败一次。实测 question/303487786 首轮 827 批挂 19 批。

**两个脚本都已加兜底**：

- `summarize-answers.mjs`：单条正文超 `SINGLE_CAP=6000` 先截断（该题最长一条 12045 字，
  单条就超 `BUDGET=7000`）；批失败则**对半拆开递归重试**（最多 4 层）
- `extract-themes-llm.mjs`：同样加了对半拆开重试

这样重跑一次就能把缺的补齐（实测 69 条 → 1 条），不用手工干预。
最后剩个位数时用 `fill-one-summary.mjs` / `fill-one-theme.mjs` 单独补，
它们会把结果同步写进 state 和最终 JSON。

**识别方法**：报错信息里能看到 JSON 已经开头（`非 JSON 数组: [{"id":"...`），
基本就是截断而不是格式错。真正的格式错通常连 `[` 都没有。

## 9. 并发会话：没有锁，会重复抓

**脚本之间不会互相感知。两个会话同时跑同一个问题 ID，会各自完整抓一遍。**

实测事故（2026-10-14，question/303487786）：

| | 会话 A | 会话 B |
|---|---|---|
| 抓取 | 3,898 条 → `Default Project/` | 3,895 条 → `zhihu-quant/` |
| ID 交集 | \multicolumn{2}{c}{3,895} |
| 交集内赞数 | \multicolumn{2}{c}{完全相同} |

两份数据**内容等价**，但白花了约 400 次请求，而且产物分散在两个目录 —— 谁手里都不完整。

**开工前的检查清单**：

```powershell
$dirs = @($env:ZHIHU_QUANT_OUT, "$env:USERPROFILE\Documents\zhihu-quant") | Where-Object { $_ }
foreach ($d in $dirs) { Get-ChildItem $d -Filter "q<ID>-*" -ErrorAction SilentlyContinue | Select-Object FullName, LastWriteTime }
```

- 已有 `-answers-full.json` → 跳过抓取（它是全流程最贵的一步）
- 已有 `-summaries.json` → 跳过摘要
- 已有 `-themes.json` / `-books-llm.json` → 跳过对应抽取
- **不要用「没看到输出」判断没跑过** —— 产物可能在另一个目录

**另一个共享资源是 `scripts/` 本身。** 多会话同时改同一批脚本会互相覆盖。
动 `scripts/` 前先看 `LastWriteTime`；改完立刻验证（`node --check` + 跑一次）。

`fetch-answers-api.mjs` **已加基于问题 ID 的文件锁**（`scripts/lock.mjs`），
检测到同 ID 正在跑会直接退出（exit 3）并打印持有者 PID 与已有产物路径：

```
[!] 另一个会话正在处理同一个目标，已退出以免重复抓取。
    持有者: pid 7832 @ HOST，开始于 2026/10/15 08:25:03
    已有产物: .../q491790104-answers-full.json（205 条）—— 直接复用即可，不必重抓。
```

设计要点：

- **活着的进程持有 → 拒绝**（不阻塞、不重试，直接让人决定）
- **陈旧锁 → 接管**：持有者进程已死，或锁存在超过 6 小时
- **只删自己写的锁**：防止把接管者的锁误删
- **异常退出也释放**（`exit` / `SIGINT` / `SIGTERM` / `SIGHUP` 都挂了清理）
- 实测 9/9 行为测试 + 1 项真实抓取集成测试通过

仍然要注意：**这个锁只保护「同一台机器上的同一个产物路径」**。
两个会话用不同的 `ZHIHU_QUANT_OUT` 指向不同目录时，锁文件不在一处，仍会各抓一遍。

## 10. 跑长任务的六个坑（都是实测踩的）

这一节从 `SKILL.md` 搬来 —— 那是路由层，不该承担操作手册的职能。

### ① 不要用 `| Select-Object -First N` 截断输出

PowerShell 停止读取管道时**上游进程会被终止**。实测 `node 全量判定 | Select-Object -First 6`，
任务在 3898 条里只跑完 752 条就被杀掉（exit code 1，像是脚本自己崩的）。

```powershell
node "$SCRIPTS\<某个长任务>.mjs" ... > "$env:TEMP\log.txt" 2>&1   # ✅ 重定向到文件，跑完再读
node "$SCRIPTS\<某个长任务>.mjs" ... | Select-Object -First 6    # ❌ 会杀掉进程
```

### ② 「脚本存在」不等于「功能存在」

`classify-content-llm.mjs` 早就有「粗筛 + 抽样」模式，跑完输出看起来完全正常。
但要求全量判定时，重跑直接返回 **「待处理 0 批」** —— 因为根本没有 `--all` 这个模式，
脚本只把「粗筛命中 + 抽样」送去判定。**加 `--all` 后同样的命令立刻开始跑 3898 条。**

**教训**：重跑出现「0 批待处理」时不要当成「已经跑完了」，
先确认这次调用传的参数**确实被脚本支持**。

### ③ 失败批写空值会让重跑永远跳过

续跑逻辑常写成 `todo = items.filter(x => !state.perAnswer[x.id])`，
但失败批如果写的是 `{kind: ''}`，这个对象是 **truthy** → 重跑时判定为「已完成」直接跳过，
那几条永远补不上。实测补跑 4 轮才清干净。

**现在三个 LLM 脚本统一以「值非空」作为完成判据**，失败时不写空值。
手工清理旧 state 的办法：

```powershell
node -e "const fs=require('fs');const p='<state.json>';const s=JSON.parse(fs.readFileSync(p,'utf8'));\
let n=0;for(const [k,v] of Object.entries(s.perAnswer))if(!v||!v.kind){delete s.perAnswer[k];n++}\
fs.writeFileSync(p,JSON.stringify(s));console.log('清除',n)"
```

### ④ 模型会臆造不存在的 ID，统计前清孤儿

LLM 逐条返回 ID 时会编造数据集里没有的 key（实测出现过 `2144820996`）。
渲染端按 ID join 真实数据所以不污染页面，但会让
「已判定 3899 / 回答 3898」这种对不上的数字出现。
**现在脚本只接受「本批内」的 ID**，`verify-output.mjs` 会复核。

### ⑤ 写进文档的每个数字，都要拿数据对账

**文档说错了比没有文档更糟** —— 下一个会话会照着错的数字做判断。

实测踩过：把「粗筛命中 + 抽样」估出来的分层虚构率直接写进 skill 文档，
而那些数是**有偏的**（抽样里塞了高赞长文）：

| 分层 | 抽样版估的 | 全量实测 | 偏差 |
|---|---|---|---|
| 200–500 字 | **0.0%** | 7.0% | 漏掉一整层 |
| 1000–3000 字 | 47.4% | 25.5% | **高估 1.9 倍** |
| 3000+ 字 | 68.4% | 60.1% | 高估 14% |
| Top20 虚构占赞数 | 60.5% | 62.6% | 尚可，但纯属巧合 |

**写完文档后跑一遍对账**，用产物 JSON 重算关键数字逐条比对。
这个检查还顺带查出了文档里的陈旧路径和断链。

### ⑥ 别用 `--out` 换路径来出「另一个口径」的产物

实测踩过：为了出「去盐选版」的综述，用 `--out` 指到另一个文件 ——
结果那个新 state 里**没有逐条摘要缓存**，827 批摘要在新文件里全空。

正确做法是让**同一份 state 存多个口径**（见 `content-kind.md` 6.5 节）：
逐条摘要与剔除无关，永远复用；只有综述按口径分别缓存。
